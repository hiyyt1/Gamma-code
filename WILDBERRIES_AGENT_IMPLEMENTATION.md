# Wildberries Менеджер — реализация Gamma

Дата проверки: 2026-10-10. Статус: **локальный/on-premise MVP с проверенным mock E2E**, не production-ready SaaS. Реальных токенов и изменений магазина при разработке не использовали.

## Архитектура и фактический runtime

`wildberries-manager` находится в существующем `gamma-agent-market/catalog.json`, категория «Бизнес / Маркетплейсы». Применение профиля использует существующие AgentMarketService, project binding в SQLite, revision/integrity pins и создание обычной сессии. Новый runner, чат, оркестратор или Skill Market не создавались.

Проверено по коду: AgentCatalog декодирует ConfigAgentV1; `packages/opencode/src/agent/agent.ts` разрешает основной профиль и его members; `SessionPrompt` и native TaskTool исполняют эту конфигурацию. UI использует совместимый SDK и V1 prompt_async. **Поддержка V2 для WB не заявляется.** Текущие V2 Credential/Core/Protocol не использованы для хранения WB токенов: существующая CredentialTable хранит value без подходящего для этой интеграции шифрования.

«Битрикс24 Разработчик» действительно присутствует: профиль, bundle навыков, четыре роли, защищённая форма, локальный MCP и серверная проверка планов. Его интеграционный тест HTTP → V1 → MCP → mock REST прошёл. Это подтверждает готовность локального механизма, а не реального портала или облачного OAuth. У 1С проверены профиль, bundle, изоляция и диагностика отсутствующего BSL runtime; тест реального Java/BSL пропущен без соответствующего окружения.

Основные файлы:

- `packages/opencode/src/wildberries/methods.ts`: проверенный каталог операций, Zod-схемы, риск, адреса, лимиты.
- `store.ts`: память секретов, права, API транспорт, пагинация, журнал намерений/изменений, подтверждение и readback.
- `mcp.ts`: стандартный MCP Server + Client через InMemoryTransport существующего runtime, семь метаинструментов.
- `packages/opencode/src/server/routes/instance/httpapi/wildberries.ts`: защищённые project routes подключения и подтверждения.
- `packages/app/src/components/wildberries-connection.tsx`: форма подключения; текущий магазин, категории, ошибки и точные планы изменений.
- `gamma-agent-market/bundles/wildberries-management`: восемь навыков с integrity manifest; исходный Python аналитический модуль.

MCP активируется только для выбранного WB-профиля, имя `gamma-wb` зарезервировано от пользовательского переопределения. При смене профиля клиент закрывается и доступ к магазину отзывается локально. Callback каждого вызова проверяет актуальность project binding/revision. Другие агенты не получают инструменты WB.

Лицензия SDK не переносится на документацию WB; из документации использованы факты интерфейса, а не копия материалов.

## Инструменты и поддерживаемые операции

Семь инструментов: `connection_status`, `search_methods`, `read`, `prepare_plan`, `execute_plan`, `verify_plan`, `analyse`. Поиск выдаёт компактные описания, запрос конкретного метода — схему, риск и лимит. Неизвестные поля/URL/методы запрещены сервером.

14 операций:

| Класс | Операции |
|---|---|
| READ | orders, sales, cards, prices, inventory, finance, campaigns, advertising_stats, reviews |
| WRITE | update_cards; несколько карточек повышают риск до HIGH-RISK |
| HIGH-RISK | update_prices, pause_campaign, update_bids, answer_review; планы нескольких операций |

GET `pause_campaign` — **изменяющий** метод. Финансовая детализация использует актуальный POST `/api/finance/v1/sales-reports/detailed`, не устаревший reportDetailByPeriod. Остатки — POST `/api/analytics/v1/stocks-report/wb-warehouses`. Статистика рекламы — GET `/adv/v3/fullstats`. Каталог намеренно ограничен; создание карточек, поставок, пополнение бюджета и удаление объектов не реализованы. При недостаточности схемы полного обновления карточки нужно подготовить ручную рекомендацию, а не терять её неизвестные поля.

READ: не более пяти страниц на вызов, явные complete/next, отдельные алгоритмы cursor/offset/rrdId/lastChangeDate. Данные сохраняются в `wb-data-<uuid>/wb-response.json`, чтобы не переполнять контекст. Интервалы по категориям/продавцу консервативные, в sandbox общий ограничитель. На 429/5xx не более двух повторов READ, Retry-After/X-Ratelimit-Retry/X-Ratelimit-Reset учитываются; ожидание свыше минуты возвращает ошибку вместо раннего повтора. На WRITE повторов нет. Редиректы запрещены, таймаут 20 секунд, лимит ответа 10 MB. Несколько процессов не координируют лимиты — это ограничение MVP.

## Навыки и делегирование

Восемь содержательных навыков: wb-api, wb-sales-analytics, wb-advertising, wb-unit-economics, wb-inventory, wb-product-optimization, wb-reviews, wb-pricing. Инструкции включают источники, порядок применения, правила интерпретации, ограничения и ссылки на контракт данных. Bundle подключается автоматически штатным discovery и защищён SHA-256 manifest.

Нативные subagents:

- `wb-sales-analyst`: динамика, ABC, аномалии.
- `wb-advertising-manager`: реклама, ДРР, предложения.
- `wb-product-manager`: карточки, отзывы, остатки.
- `wb-financial-analyst`: себестоимость, расходы, рентабельность.

Runtime-имена имеют штатный префикс `gamma-`. Помощники получают подходящие навыки и READ/аналитику, не получают prepare/execute/verify планов магазина. Bash, webfetch/websearch, произвольный TaskTool и внешние каталоги запрещены policy. Доступ к ресурсам своего bundle разрешён только на чтение. Только ведущий может делегировать перечисленным четырём помощникам и инициировать изменения. Credentials не входят в tool arguments/prompts/environment дочерних процессов; выбор чужого магазина аргументом инструмента невозможен.

## Аналитика и пять бизнес-сценариев

`skills/wb-unit-economics/scripts/analytics.py` — переиспользуемый Python 3 stdlib модуль. Gamma запускает фиксированный проверенный script через Bun.spawn, без shell; JSON job через stdin, без credentials, timeout 60 сек. Требуется Python 3, pip-зависимостей нет.

Реализованы Decimal-расчёты ДРР, валовой прибыли/маржи, результата и маржи после известных затрат, ABC, сравнения периодов, median/MAD аномалий, оборачиваемости при известном среднем запасе, дней покрытия и объёма пополнения. Сопоставление точных nmID/vendorCode/barcode выявляет неоднозначность; ведущие нули сохраняются в текстовых идентификаторах. Есть импорт UTF-8 CSV и первого листа XLSX; формулы и XML entities не выполняются, объём ZIP ограничен. JSON — нормализованные строки или поддержанные артефакты READ. Подробный контракт: `skills/wb-unit-economics/references/input.md`.

Продажи, возвраты, заказы, выплаты и финансовые расходы разделены. Неизвестная себестоимость даёт null прибыли; неизвестные расходы перечислены, а не подменены фактами. Расходы рекламы нельзя одновременно дублировать в продажах и ad-строках. Возврат увеличивает восстановленную стоимость запасов только при явном resalable=true. raw finance не предполагает знаки возврата комиссии/эквайринга: эти суммы на возврате остаются неизвестными до сверки. raw finance учитывает основные поля и помечает прочие удержания неизвестными — это не бухгалтерский расчёт всех компенсаций и налогов. Финансовые отчёты и статистику продаж нельзя складывать как независимую реализацию.

Каждый запуск создаёт `wb-report-<uuid>/analysis.json`, `products.csv`, `products.xlsx`, `report.md` в обычной файловой панели. JSON содержит исходные SHA-256, период, таблицы и ограничения. В экспортированных строках нейтрализована формульная инъекция. Отчёт расчёта служит основой для русского бизнес-объяснения ведущим; качественные гипотезы отдельно от фактов. При chart=true модуль также создаёт SVG-график дневной выручки с положительными/отрицательными значениями, встроенный в Markdown.

Все пять намерений описаны в ведущем профиле и навыках и доступны обычным сообщением:

1. Падение продаж: равные периоды, реализация, остатки/цены/реклама, доказательства и гипотезы.
2. Реклама: расходы, атрибуция, ДРР, предложения, подтверждённый план изменений.
3. Прибыль: финансовые данные плюс импорт себестоимости, частичный расчёт при неизвестных статьях.
4. Карточки: базовые проверки полноты, содержательные предложения, точный plan и readback.
5. Остатки: скорость, покрытие, lead/safety days, предложения поставки.

Без магазина доступны файлы и расчёты; подключение не требуется искусственно. В диалоге проекта подключение/подтверждение через UI автоматически отправляет продолжение в **существующий** V1 prompt_async, без токенов и approvalKey. Если отправка не удалась, UI сообщает об этом. В карточке Market без текущей сессии продолжение не запускается.

## Подключение, права и безопасность

По [официальной документации](https://dev.wildberries.ru/en/docs/openapi/api-information) и [правилам сервисной авторизации](https://dev.wildberries.ru/news/144): тестовый токен (`acc=2`, `t=true`) предназначен для sandbox; персональный (`acc=3`, `for=self`, `t=false`) — собственная/on-premise интеграция продавца; сервисный (`acc=4`) привязан к сервису. В этой реализации базовые и сервисные токены отклоняются. Облачное коммерческое использование персональных токенов не реализовано.

Для клиента:

1. Выбрать агента и проект. Для файлов — загрузить CSV/XLSX, сформулировать задачу.
2. Для sandbox создать тестовый токен в кабинете WB, открыть панель проекта «Wildberries Менеджер» и ввести токен в password-поле. Finance, inventory и fullstats сейчас не предоставляются этим адаптером в sandbox; используйте выгрузки.
3. Для разрешённого личного on-premise кабинета администратор явно включает `GAMMA_WB_ON_PREMISE=1`. Требуются персональный токен и только нужные категории. По умолчанию этот режим закрыт.
4. Настроить пароль сервера Gamma, HTTPS (или localhost), выбрать категории и при необходимости разрешить подготовку изменений. READ достаточно для аналитики.

JWT декодируется локально только для предварительных ограничений (`acc`, `for`, `t`, `exp`, `s`). Подлинность и доступ проверяет WB каждым ping/запросом; локальная расшифровка не называется криптографической проверкой. Категории пересекаются с выбором пользователя и результатами probes. Bit 30 блокирует запись. Sandbox использует sandbox-hosts и seller sid из токена, принятого WB ping; personal дополнительно получает seller-info. Пользователь не может задать API host.

Один магазин на каноническую директорию проекта; разные магазины — разные проекты. Секреты и ключ подтверждения только в памяти до 8 часов/expiry, затем удаляются; после перезапуска нужно переподключение. В браузере approval capability также только в памяти. Статусы не содержат токены. Переподключение существующего магазина запрещено во время выполняющейся задачи; первое подключение допустимо во время ожидания ответа пользователем. Disconnect отменяет запросы и удаляет локальный доступ; глобально токен отзывается в кабинете WB. Автоматического API отзыва WB здесь нет.

Все WRITE требуют UI-подтверждения точных операций — более строгий MVP-режим, чем постоянное разрешение на произвольные записи. Модель не может передать confirm=true. Подтверждение ограничено текущим проектом, секретной browser capability и сроком плана 10 минут. Сервер повторно проверяет права перед исполнением.

Журнал в `<Global.Path.data>/wildberries-audit` вне project files: продавец, время, метод, plan, целевые значения, исход исполнения и проверки; без токенов. До HTTP WRITE эксклюзивно создаётся и fsync-ится durable intent. Повтор идентичной операции блокируется даже после переподключения/перезапуска. Это сознательно консервативный механизм: автоматического снятия блока нет; неоднозначный результат требует сверки, не нового ключа для повтора. Принятие операции записывается как accepted_unverified. verify_plan автоматически сверяет карточки, цены и остановку кампании; ставки/ответы пока требуют отдельного чтения и не получают ложный verified=true.

Изоляция предназначена для доверенного однопользовательского backend Gamma. Это не защита от администратора ОС, не RBAC многопользовательского SaaS и не KMS. Административные UI сторонних MCP не запускаются и не публикуются.

## Что нужно до коммерческого запуска

Разрешённое тестовое подключение и реальные безопасные READ по каждой категории; затем согласованные controlled WRITE/readback на тестовых объектах. Проверка рассуждений и продолжения задач с выбранной LLM, нагрузочные сценарии, обработка всех финансовых postings и reconciliation асинхронных задач. Нужны правила сроков хранения отчётов/аудита и восстановление неоднозначных записей.

Для облачного SaaS: оформление сервисной интеграции WB/Каталога, сервисный секрет и требуемая авторизация запросов, OAuth/token lifecycle по актуальным правилам WB, tenant/user RBAC, шифрованный vault/KMS, распределённые лимиты, полноценный операционный аудит и мониторинг. Персональный on-premise флаг не заменяет эти условия. Расширение API-каталога — отдельная последующая возможность, не заявленные как уже работающие.
