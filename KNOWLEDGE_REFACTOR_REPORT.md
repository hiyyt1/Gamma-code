# Рефакторинг базы знаний Gamma

## Причина пустой карты

Проверен рабочий `GET /product/knowledge/verify` на порту 4108. На момент исследования он возвращал корень `~/.local/share/gamma-dev/knowledge`, версию публикации 0, 0 пространств, материалов и связей, без ошибок файловой проверки. Поэтому сообщение «Серверное хранилище пусто» соответствовало состоянию этого сервера, а не сбою WebGL.

Страница выбирает источники текущего пространства из активного хранилища. Локальная база `gamma-knowledge-v1` в IndexedDB привязана к origin и профилю браузера; наличие данных в другом профиле, на другом порту или в другом серверном каталоге не наполняет эту карту. При подтверждённой серверной привязке интерфейс использует серверные данные, не объединяя их автоматически с IndexedDB.

Обнаружены два старых набора:

- В `packages/app/src/utils/knowledge.ts` было встроенное демо: 20 узлов, 23 связи, пустой массив пространств, одинаковые описания, без текстов документов. Оно заменено новым каталогом; пользовательское хранилище при этом не изменяется.
- `script/knowledge-base/data.mjs` и `seed.mjs` содержат отдельную тестовую базу: 36 материалов, 6 тематических сущностей, 64 связи. Скрипт явно записывает её в IndexedDB конкретного браузера. Он не запускается страницей и не публикует данные на сервер. Скрипт и ранее записанные записи сохранены.

Причина «Скоро появится» — явная ветка `if (state.demo) show("soon")` в обработчике открытия материала. Теперь демо использует настоящий просмотрщик документов.

Обычный пользовательский профиль браузера недоступен из изолированного тестового профиля. Наличие старых данных именно в нём не утверждается; предусмотрены просмотр сохранённых локальных данных, резервная копия и явный импорт.

## Реализация

- Отдельный каталог `knowledge-demo.ts`: пространство **«Кофейня Зёрна — демо»**, 96 узлов, 146 связей, 40 документов и заметок, 12 бизнес-процессов.
- Демо открывается при пустом сервере, ничего не записывает при просмотре и сохраняет режим в URL `?demo=ziorna` при обновлении страницы.
- Документы открываются в существующем просмотрщике, Markdown проходит очистку и отображается в изолированном iframe. В демо отсутствует действие редактирования.
- Явная кнопка создаёт самостоятельную редактируемую копию: новые идентификаторы пространства, узлов, связей и ссылок на исходные документы. Существующие пространства не заменяются.
- Карточка показывает бизнес-тип, описание, свойства, исходный документ, входящие и исходящие связи. Переход по связи выбирает узел и фокусирует камеру; скрывающий его фильтр сбрасывается.
- Поиск учитывает бизнес-тип и содержимое документа; фильтр бизнес-типов строится из данных текущего пространства. Редактор допускает собственный бизнес-тип и выбор исходного документа.
- Направленные связи отображаются стрелками независимо от ручного или демонстрационного происхождения.
- Добавлен явный переход к сохранённым локальным данным при активном серверном состоянии. Старые записи не очищаются и не перезаписываются.

## Модель и совместимость

Технический `type` сохранён: `document`, `note`, `link`, `entity`, `project`. Это сохраняет поведение существующих просмотрщиков и значков. Добавлены необязательные поля:

| Поле | Назначение |
| --- | --- |
| `entityType` | Расширяемый бизнес-тип, непустая строка до 120 символов |
| `properties` | Строковые свойства сущности |
| `documentID` | Исходный материал того же пространства |

В демо представлены компания, подразделение, сотрудник, должность, клиент, клиентский сегмент, поставщик, продукт, ингредиент, рецептура, процесс, проект, документ, заметка, ссылка, договор, регламент, финансовый показатель, оборудование и локация.

Связь хранит идентификаторы `source`/`target`, строковый тип, происхождение и метаданные. Предустановки дополнены `WORKS_IN`, `HAS_ROLE`, `BELONGS_TO`, `VISITS`, `SUPPLIES`, `STORED_IN`, `LOCATED_IN`, `RESPONSIBLE_FOR`, `CONTAINS`, `REGULATES`, `AGREEMENT_WITH`. Сохранены прежние `RELATED_TO`, `DEPENDS_ON`, `USES`, `PART_OF`, `DESCRIBES`, `COMPLEMENTS` и исторические пользовательские названия связей. `RELATED_TO` считается симметричным при проверке повторов; остальные типы направлены.

Проверяются отсутствующие конечные узлы, связь с собой, выход за пространство, повторные связи в редакторе, пустой тип, HTTP/HTTPS URL и ссылки на исходный материал. Удаление документа очищает у оставшихся узлов ссылку на него, сохраняя их содержимое. Сервер также проверяет структурную целостность перед публикацией.

Миграция аддитивная: старые записи без новых полей продолжают читаться; версия IndexedDB и идентификаторы не изменяются. Массовой перезаписи старых файлов нет. API возвращает `modelVersion: 2`. Перед отправкой новых полей frontend проверяет поддержку модели: старый сервер иначе мог бы отбросить их при декодировании. При несовместимости запись останавливается до загрузки файлов и публикации с понятным сообщением.

## Структура компании и материалов

Три кофейни, центральный склад, три отдела, шесть сотрудников, четыре должности, три поставщика, три клиентские группы и три сегмента. Меню включает четыре напитка и пять ингредиентов; три единицы оборудования, три проекта.

Материалы: 12 рабочих регламентов процессов, 4 рецептуры, 3 договора, 3 финансовых отчёта, 3 паспорта проектов, 6 заметок наблюдений, 9 документов и регламентов устройства сети. Ещё две ссылки используют зарезервированный домен `example.com`; их реальные учебные материалы доступны внутри базы. Это не действующие порталы.

Примеры исследуемых цепочек:

- Мария → отвечает за → калибровка → использует → зерно ← поставляет ← обжарочная ← договор с ← договор поставки.
- Павел → отвечает за → запуск меню → зависит от → обучение ← регламентирует ← регламент обучения.
- Клиент «Лист» → относится к → офисные команды ← описывает ← документ о сегментах.
- Проект осеннего меню → использует → сироп ← содержит ← рецептура латте → описывает → продукт ← описывает ← показатель маржи.

Каждый узел маркирован как вымышленный, тексты документов содержат явное предупреждение. Цены, люди, адреса и условия не относятся к реальным организациям.

## Хранение

Основной механизм не заменён: сервер хранит публикацию в `_registry.json`, материалы в каталогах пространств, оригиналы по проверяемым хешам. Публикация выполняется под файловой блокировкой через атомарную смену подготовленного каталога. Версия защищает от устаревшей записи, request ID — от повторной публикации. Направление, типы и дополнительные свойства сохраняются в реестре; `links.json` остаётся совместимым двунаправленным индексом соседства для файловых инструментов.

IndexedDB `current` и исходные Blob сохраняются отдельно от серверного кеша `server:<URL>` и кеша оригиналов `remote:<hash>`. Явный импорт объединяет записи без замены конфликтующих ID, проверяет оригиналы и серверные файлы. Ошибки импорта не очищают локальную базу. Нельзя считать кеш другого сервера или другого origin автоматической миграцией.

Демо находится в коде приложения, поэтому детерминированно воспроизводится и не создаёт копий при перезагрузке. Только действие «Создать редактируемую копию» публикует пространство. Текстовые демонстрационные документы сохраняются как материалы; у них нет выдуманных отсутствующих PDF/DOCX-оригиналов.

## Визуализация и производительность

Сохранены Three.js/3d-force-graph, объёмные сферы, лавандово-голубая палитра, тонкие связи, свободная раскладка, вращение, масштабирование, панорамирование и перемещение узлов. Нет центрального узла Gamma, групповых контейнеров или жёстких кластеров.

Используется существующая ограниченная детерминированная раскладка: 150 шагов при изменении данных, без постоянной физической симуляции (`cooldownTicks(0)`). После 80 узлов используются упрощённая геометрия и плотный режим материала; общие материалы переиспользуются. Подписи проходят отсечение пересечений и ограничиваются 22 одновременно. Поиск и выбор сохраняют тот же canvas.

Всего успешно завершены **22 различных браузерных сценария**, с указанным повторным прогоном DOCX. Тесты дополнительно проверяют выбор узла кликом, повторный выбор, перетаскивание, панорамирование, отмену редактора, направление связи, защиту от повторов и конфликт между вкладками.

Сохранённую копию отдельно прочитал новый процесс `KnowledgeStore` из `/tmp/gamma-knowledge-refactor-final/knowledge`: версия 3, 1 пространство, 96 источников, 146 связей, 20 бизнес-типов, свойства на всех узлах, все 40 текстов сохранены; `verify.errors = []`. Это проверка сохранности между процессами без остановки рабочего сервера.

Измерения на этой машине, Chromium с программным WebGL, не универсальная гарантия FPS:

- Демо 96 узлов: 90 измеренных кадров, медиана 33,3 мс, p95 33,4 мс.
- Регрессионная карта 158 узлов: glow — медиана 50 мс, p95 66,7 мс; смешанные материалы — медиана 33,3 мс, p95 50 мс.
- Детерминированная раскладка 120 узлов прошла отдельную проверку конечности координат и неизменности результата при перестановке входных массивов.

В промежуточных прогонах выявлены и устранены ошибки селекторов: текст Markdown находится внутри sandboxed iframe; у фильтра бизнес-типа теперь есть явное доступное имя; статус синхронизации проверяется отдельно от новой кнопки просмотра локальных данных. Регрессионные фикстуры перенесены на независимый пустой тестовый сервер, чтобы публикация копии демо не нарушала их предпосылки.

Отдельный сбой dev-окружения: Vite при первом обращении к `mammoth` выполняет позднюю оптимизацию и полную перезагрузку страницы. Лог подтвердил причину; после оптимизации DOCX/Markdown и миграция проходят. Кроме того, запись HTML-отчёта Playwright в наблюдаемую директорию может перезагрузить другой параллельный тест; повторные прогоны использовали `--reporter=line` и отдельные каталоги `/tmp`. Приложение и рабочий сервер ради обхода этого поведения не перезапускались; конфигурация Vite не изменялась. Проверка production-сборки прошла.

## Эксплуатационные ограничения

- Рабочий backend 4108 не перезапускался, пользовательские пространства не изменялись. Чтобы он обслуживал новые поля и копирование, ему нужно запустить обновлённый код. Чтение демо работает независимо от наличия пользовательского пространства.
- Ограничение запуска взято из `packages/app/AGENTS.md`: «NEVER try to restart the app, or the server process, EVER.» Поэтому проверенный новый backend запускался отдельно, а рабочий процесс оставлен нетронутым. Старый backend получает понятный отказ до записи новых полей вместо их молчаливого удаления.
- Для проверки используются отдельные серверные корни в `/tmp` и изолированные браузерные профили. Файловая устойчивость проверяется новым процессом; рабочий сервер ради проверки не останавливается.
- Существующий лимит раскладки — 250 узлов; поиск остаётся доступным, но большие пространства требуют отдельной стратегии отображения. Рефакторинг проверяется на целевом объёме около 100 узлов и плотной тестовой карте.
- Нет автоматического извлечения сущностей из PDF/DOCX, синхронизации прямых внешних правок файлов, многопользовательских прав или кластерного хранилища. Эти возможности не имитируются демо.
